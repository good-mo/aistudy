# 企业级性能测试指南（Performance Testing Guide）

> 适用对象：Test Generation Agent Toolkit 关键 API 与测试生成链路
> 标准依据：ISO/IEC 25010（性能效率）、ISTQB 性能测试方法论

## 一、性能测试维度

企业级性能测试从 **基准 → 负载 → 压力 → 容量 → 稳定性 → 峰值** 六个维度系统化评估，并沉淀可回归的**性能基线**。

```
          并发/负载
             ↑
  稳定性 ─── 基准 ─── 峰值
             ↓
          容量/压力
```

| 维度 | 目的 | 示例 |
|------|------|------|
| **基准 Baseline** | 单请求最小延迟/吞吐基线 | 健康检查 P95 < 10ms |
| **负载 Load** | 正常业务负载下指标 | 50 并发持续 5min |
| **压力 Stress** | 超负载下的表现/拐点 | 500 并发观察拐点 |
| **容量 Capacity** | 系统能支撑的最大规模 | 最大并发数/最大数据量 |
| **稳定性 Soak** | 长时间运行是否有内存泄漏/劣化 | 持续 1h |
| **峰值 Spike** | 突发流量冲击 | 0→300 瞬时 |

## 二、性能指标定义

| 指标 | 说明 | 本项目关注 API |
|------|------|---------------|
| **响应时间 RT** | 平均/P95/P99 | `/api/cases`、`/api/tasks/{id}` |
| **吞吐量 TPS** | 每秒请求数 | `/health`、`/api/cases` |
| **并发数** | 同时处理请求数 | `/api/generate?async_mode=true` |
| **错误率** | 失败请求占比 | 所有接口 < 1% |
| **资源使用** | CPU/内存/连接数 | 任务队列、WebSocket |
| **排队时间** | 任务队列延迟 | `/api/tasks` 任务 pending→running |

### 建议性能基线（本工具集，开发机 4C8G 参考）

| API | 并发 | 平均 RT | P95 RT | 错误率 | 备注 |
|-----|------|---------|--------|--------|------|
| `/health` | 100 | < 5ms | < 10ms | 0% | 无 IO |
| `/api/cases` 列表 | 100 | < 30ms | < 50ms | < 1% | SQLite |
| `/api/cases` 创建 | 100 | < 30ms | < 50ms | < 1% | 写库 |
| `/api/cases/{id}` 详情 | 200 | < 20ms | < 30ms | < 1% | 主键查 |
| `/api/defects` 列表 | 100 | < 30ms | < 50ms | < 1% | SQLite |
| `/api/tasks/{id}` | 200 | < 15ms | < 25ms | < 1% | 内存态 |
| `/api/tasks` 提交 | 100 | < 20ms | < 40ms | < 1% | 入队 |
| `/api/projects/scan` | 10 | < 2s | < 5s | < 1% | 磁盘 IO |
| `/api/reports/generate` | 5 | < 5s | < 8s | < 1% | 含生成 |

## 三、性能测试场景设计

### 3.1 基准测试（每版本回归）

对 `GET /health`、`GET /api/cases`、`GET /api/cases/{id}` 各跑 100 次，记录平均/P95/P99，与基线对比，偏差 > 30% 即告警。

### 3.2 负载测试（核心流程）

模拟测试工程师真实操作序列：
1. 登录/健康检查（`GET /health`）
2. 用例库列表查询（`GET /api/cases?limit=100`）
3. 创建用例（`POST /api/cases`）
4. 查询任务状态（`GET /api/tasks/{id}` 轮询）
5. 缺陷查询（`GET /api/defects`）

以 50 并发、持续 5 分钟观察资源与延迟。

### 3.3 压力测试（找拐点）

逐步增加并发：50 → 100 → 200 → 400，观察 RT 突变点（拐点），确定系统最大支撑并发。

### 3.4 容量测试

- **数据量**：插入 1 万条用例，验证 `/api/cases` 列表查询延迟不劣化。
- **任务量**：批量提交 500 个任务，验证队列不丢、状态一致。

### 3.5 稳定性测试（Soak）

中等负载（30 并发）持续运行 1 小时，监控内存/连接数是否线性增长（泄漏检测）。

### 3.6 峰值测试（Spike）

瞬时从 0 拉到 300 并发再回落到 0，观察是否出现 5xx、任务丢失。

## 四、性能测试执行工具

### 4.1 内置 pytest 压测（`tests/performance/`，可离线运行）

基于纯 Python + threading 的轻量压测，无需外部工具，CI 可直接跑：

```bash
# 基准
pytest tests/performance/test_api_benchmark.py -v

# 并发/负载/压力
pytest tests/performance/test_api_concurrency.py -v
```

### 4.2 外部专业工具（生产环境推荐）

| 工具 | 适用 | 命令示例 |
|------|------|---------|
| **wrk** | HTTP 基准 | `wrk -t4 -c100 -d30s http://localhost:8000/api/cases` |
| **locust** | 复杂场景/分布式 | Python 脚本定义用户行为 |
| **k6** | 云原生/CI | `k6 run script.js` |
| **JMeter** | 全功能/企业 | GUI 或 CLI |

## 五、性能测试流程（企业级）

```
1. 明确性能目标（基线 SLA）
2. 搭建与生产一致的测试环境（配置/数据量）
3. 准备测试数据（万级用例库）
4. 基准测试 → 记录基线
5. 负载/压力/容量/稳定性/峰值 逐级执行
6. 监控资源（CPU/内存/连接/GC）
7. 结果对比基线 → 定位瓶颈 → 优化 → 回归
8. 输出性能测试报告，沉淀到 CI 门槛
```

## 六、瓶颈定位与优化建议

| 常见瓶颈 | 本项目对应 | 优化方向 |
|---------|-----------|---------|
| SQLite 写串行 | 用例/缺陷写入 | 读多写少场景 OK；高并发写切 PostgreSQL |
| 同步 LLM 长任务 | `/api/generate` 同步模式 | 强制 async_mode + 任务队列（已具备） |
| 报告生成 CPU 密集 | `/api/reports/generate` | 结果缓存、异步生成 |
| WebSocket 长连接 | `/ws/generate` | 连接数上限、心跳检测 |
| 无连接池 | 每次请求建连 | 引入 DB 连接池/缓存（Redis） |

## 七、性能测试报告模板要点

- 环境描述（硬件/软件/数据规模）
- 各场景的 RT/TPS/错误率/资源使用表
- 与基线对比（劣化/优化百分比）
- 瓶颈根因分析
- 结论：达标/不达标 + 建议
